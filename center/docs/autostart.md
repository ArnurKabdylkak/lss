# Автозапуск при включении питания

Контейнеры уже помечены `restart: unless-stopped`: как только поднялся
демон Docker, центр и видеотракт возвращаются сами. Остаётся решить,
**кто запускает сам Docker** — и на Windows это не так очевидно, как на
Linux.

Имитатор комнаты намеренно оставлен без политики перезапуска: после
перезагрузки он ожил бы сам и подмешал выдуманные показания к
настоящим. Его поднимают руками на время проверки.

---

## Windows-хост

Главное, что нужно знать: **Docker Desktop работает в сеансе
пользователя**. Пока никто не вошёл в систему, демона нет, и
контейнеры не поднимутся, сколько бы политик перезапуска вы ни
поставили. Отсюда два пути.

### Путь А. Docker Desktop и автоматический вход (проще)

1. Docker Desktop → Settings → General → **Start Docker Desktop when
   you log in**.
2. Настроить автоматический вход в систему под учётной записью
   дежурного (`netplwiz`, снять «Требовать ввод имени пользователя и
   пароля»).

Работает без скриптов: после подачи питания машина входит в сеанс,
Docker Desktop стартует, контейнеры поднимаются политикой перезапуска.

Чем платим: пароль учётной записи хранится в системе, а машина после
включения оказывается в разблокированном сеансе. Для пульта в
закрытом помещении это приемлемо, для машины в коридоре — нет.

### Путь Б. Движок Docker в WSL и задача планировщика (надёжнее)

Вход пользователя не нужен: задача выполняется от SYSTEM при старте
системы.

1. Установить в WSL-дистрибутиве (например, Ubuntu) пакет
   `docker.io` — это движок Docker, отдельный от Docker Desktop.
2. Положить репозитории в `C:\mchs\` (пути правятся в скриптах).
3. Зарегистрировать задачу от администратора:

```powershell
powershell -ExecutionPolicy Bypass -File deploy\windows\install-task.ps1
```

Задача запускает [start-mchs.ps1](../deploy/windows/start-mchs.ps1) с
ключом `-UseWsl`: скрипт ждёт готовности демона до десяти минут (после
подачи питания он поднимается не сразу), затем выполняет
`docker compose up -d`. Ход записывается в
`autostart.log` рядом с `compose.yaml`.

Проверить, не дожидаясь перезагрузки:

```powershell
Start-ScheduledTask MCHS-Center
Get-Content C:\lss\center\autostart.log -Tail 20
```

> Скрипты написаны, но на Windows не проверены: под рукой был только
> Linux. Синтаксис и логика ожидания демона прямолинейны, однако
> первый запуск стоит сделать вручную и посмотреть журнал.

### Панель на рабочем месте

Чтобы на экране сразу открывался пульт, добавьте ярлык браузера в
автозагрузку (`shell:startup`):

```
"C:\Program Files\Google\Chrome\Application\chrome.exe" --kiosk ^
  --autoplay-policy=no-user-gesture-required http://localhost:8080/
```

Второй ключ снимает запрет на автозапуск видео — без него дежурному
придётся нажимать «Показать поток» на каждой камере.

## Linux-узлы

### Центр

```bash
sudo cp deploy/systemd/mchs-center.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now mchs-center
```

Юнит ждёт `docker.service` и сеть, затем поднимает тот же профиль
`video`. Пересборка образов при старте намеренно не делается: узел
должен подниматься после отключения питания, а не ждать сборку.

### Сборщик на Raspberry Pi

```bash
sudo cp deploy/systemd/mchs-collector.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now mchs-collector
```

`Restart=always` и снятый лимит перезапусков: обрыв связи с центром —
штатное состояние сборщика, а не повод уйти в отказ. Без него платы
останутся без приёмника, а буфер копится только на нём.

## Что проверить после настройки

| Проверка | Как |
|---|---|
| Контейнеры возвращаются | Перезагрузить узел, через 2–3 минуты: `docker ps` |
| Панель отвечает | `curl -o /dev/null -w "%{http_code}" http://localhost:8080/` → `200` |
| Камеры поднялись | `GET /api/v1/cameras` → `status: live` |
| Имитатор не ожил сам | В `docker ps` нет контейнера `simulator` |
| Журнал автостарта (Windows) | `Get-Content autostart.log -Tail 20` |
