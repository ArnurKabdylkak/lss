# mchs-backend

Сервис сбора телеметрии с устройств по UDP. Приёмный тракт основан на
`firmware/tools/receiver`, разложенном по чистой архитектуре.

## Запуск

```
go run ./cmd/telemetryd -listen :5005 -http :8080 -csv telemetry.csv
```

| Флаг       | Переменная      | По умолчанию | Назначение                              |
|------------|-----------------|--------------|-----------------------------------------|
| `-listen`  | `MCHS_LISTEN`   | `:5005`      | адрес UDP-приёмника                     |
| `-http`    | `MCHS_HTTP_ADDR`| `:8080`      | адрес HTTP API (пусто — не поднимать)   |
| `-csv`     | `MCHS_CSV`      | —            | файл CSV                                |
| `-silence` | `MCHS_SILENCE`  | `3s`         | пауза, после которой устройство пропало |
| `-buffer`  | `MCHS_BUFFER`   | `256`        | ёмкость очереди пакетов                 |
| `-quiet`   | `MCHS_QUIET`    | `false`      | не печатать каждый пакет                |

Видеонаблюдение (подробнее — ниже):

| Флаг             | Переменная           | По умолчанию      | Назначение                       |
|------------------|----------------------|-------------------|----------------------------------|
| `-rooms`         | `MCHS_ROOMS`         | —                 | YAML с раскладкой объекта (комнаты) |
| `-cameras`       | `MCHS_CAMERAS`       | —                 | плоский список камер, без комнат  |
| `-video-root`    | `MCHS_VIDEO_ROOT`    | `/tmp/mchs-video` | каталог сегментов                |
| `-video-prefix`  | `MCHS_VIDEO_PREFIX`  | `/video`          | путь раздачи трансляций          |
| `-video-segment` | `MCHS_VIDEO_SEGMENT` | `2s`              | длительность сегмента            |
| `-video-window`  | `MCHS_VIDEO_WINDOW`  | `6`               | сегментов в плейлисте            |
| `-ffmpeg`        | `MCHS_FFMPEG`        | `ffmpeg`          | путь к ffmpeg                    |
| `-panel`         | `MCHS_PANEL`         | —                 | каталог собранной панели; пусто — не раздавать |

## Скрипты

`make` без аргументов показывает список целей. Основные:

| Цель | Что делает |
|------|------------|
| `make up` / `make down` | поднять / остановить сервис в контейнере |
| `make logs` / `make ps` | журнал и состояние контейнера |
| `make devices` / `make csv` | состояние устройств и CSV из тома |
| `make simulate` | слать телеметрию, как это делает плата |
| `make smoke` | сквозная проверка на отдельном стеке |
| `make run` | запустить локально, без контейнера |
| `make test` / `make vet` / `make build` | тесты, проверки, сборка бинаря |

`scripts/simulate.sh` повторяет контракт прошивки (ARCHITECTURE.md §2.1):
показания раз в 200 мс, события `key` и `relay` по ходу. Нужен, пока платы
нет под рукой, и позже — для разработки сборщика. Скорость нагрева
задаётся `MCHS_SIM_HEAT` (°C/с), чтобы увидеть срабатывание защиты.

`scripts/smoke.sh` поднимает **отдельный стек на своих портах** (15005 и
18080), поэтому запускается рядом с рабочим сервисом и не мешает ему; стек
и том удаляются при выходе, в том числе при ошибке. Проверяет приём,
отбрасывание битого пакета, все три маршрута API, запись всех видов
событий в CSV и сохранность хвоста CSV при остановке.

## Запуск в контейнере

```
docker compose up --build -d
```

Образ собирается двумя стадиями и весит 6.8 МБ: сервис использует только
стандартную библиотеку, поэтому статический бинарь кладётся в `scratch`.
Тесты выполняются внутри сборки. Процесс работает под UID 65534 с файловой
системой только для чтения; CSV пишется на том `/data`. Настройки
передаются переменными `MCHS_*`, часовой пояс — `TZ`.

## HTTP API

- `GET /healthz`
- `GET /api/v1/devices` — последнее состояние всех устройств
- `GET /api/v1/devices/{id}` — состояние одного (id — IP устройства)
- `GET /api/v1/rooms` — комнаты объекта с тренажёрами, пушкой и камерами
- `GET /api/v1/rooms/{id}` — одна комната
- `POST /api/v1/rooms/{id}/session` — открыть занятие (тело: `{"examinee":"ФИО"}`)
- `POST /api/v1/rooms/{id}/session/finish` — завершить занятие и получить результат
- `GET /api/v1/rooms/{id}/sessions` — последние занятия комнаты
- `GET /api/v1/cameras` — камеры и состояние их трансляций
- `GET /api/v1/cameras/{id}` — одна камера
- `GET /video/{id}/index.m3u8` — трансляция камеры (HLS)

## Комнаты объекта

Объект состоит из комнат; в комнате стоят тренажёры, тепловая пушка со
своими уставками и камеры, которые её снимают. Раскладка задаётся одним
файлом — образец: [rooms.example.yaml](rooms.example.yaml).

```yaml
site: obj-17
rooms:
  - id: room-1
    name: "Комната 1 — тренажёрный зал"
    devices:
      - {id: obj-17-bike-1,   name: "Велосипед",         kind: bike}
      - {id: obj-17-stairs-1, name: "Лестница",          kind: stairs}
      - {id: obj-17-load-1,   name: "Силовая установка", kind: load}
    heater:
      device: obj-17-heater-1
      limit_c: 60       # порог отключения
      resume_c: 50      # возврат, обязательно ниже порога
    cameras:
      - {id: room1-cam-1, name: "Зал, общий план", url: "rtsp://…"}
      - {id: room1-cam-2, name: "Лестница и груз", url: "rtsp://…"}
```

```
go run ./cmd/telemetryd -rooms rooms.yaml -video-root /tmp/mchs-video
```

Виды тренажёров: `bike`, `stairs`, `load`, `heater`, `stand`. Загрузка
падает при старте, если вид неизвестен, устройство или камера приписаны
к двум комнатам, температура возврата не ниже порога — такие ошибки
должны быть видны сразу, а не в виде тишины на экране.

Файл с комнатами заменяет `-cameras`: камеры описываются внутри своих
комнат. Задать оба сразу нельзя — центр откажется стартовать.

### Сборщики помещений

На объекте три сборщика — по одному на помещение (`/data/lss/collector`).
Программа у всех одна, различаются только адреса и состав обвязки:

| Сборщик | Адрес | Помещение | Чем заведует |
|---|---|---|---|
| `obj-17-rpi-1` | 192.168.1.10 | теплокамера | пушка, свет, вытяжка, платы тренажёров |
| `obj-17-rpi-2` | 192.168.1.11 | дымокамера, комната 1 | дым, прожекторы, стробоскоп, звук, свет, вытяжка |
| `obj-17-rpi-3` | 192.168.1.12 | дымокамера, комната 2 | то же плюс «Завалы» |

Соответствие задаётся полем `collector` комнаты в `rooms.yaml`, и из
него же центр понимает, **кому отдавать команду**: сборщик называет
себя в каждой выгрузке (`collector_id`), а центр отбирает команды,
адресованные ему самому и его платам. Без этого первый опросивший
забирал бы чужие команды, и у соседа они бы пропали.

```
сборщик → POST /api/v1/telemetry {"site_id":"obj-17","collector_id":"obj-17-rpi-2", …}
         ← {"accepted": N, "commands": [ только его команды ]}
         → POST /api/v1/acks [ что исполнено, что отклонено и почему ]
```

Входящих соединений у сборщика нет: команды возвращаются в ответе на
выгрузку, и задержка исполнения равна периоду обращения (1 с).
Команды помещения адресуются сборщику, а не отдельным реле: какое реле
за что отвечает, знает он.

### Подготовка помещения

```
POST /api/v1/rooms/{id}/prepare
```

Переводит комнату в «Подготовку», включает оборудование командой
`prepare` сборщику комнаты и заводит таймер. Состав оборудования знает
сборщик: в теплокамере это светильники и пушка, в дымокамере —
дымогенератор, стробоскоп, прожекторы и акустика. Возврат комнаты в
«Ожидание» гасит его командой `prepare_stop`.

**Оборудование с дискретным управлением центр включает сам.** Кнопок
«включить светильники», «включить нагрев», «сбросить препятствие» в
панели нет: одним стартом подготовки уходит всё, что нужно комнате —

```
prepare     → сборщику комнаты (свет, вытяжка, дым, стробоскопы, акустика)
set_limits  → пушке: порог и возврат из rooms.yaml
heater_on   → пушке: разрешение работать
set_code    → стойке набора: новый код этой тренировки
```

Уставки защиты берутся из раскладки объекта, а не из поля ввода:
значения, которыми определяется безопасность зала, не должны зависеть
от того, что сегодня напечатал дежурный. Если уставки не ушли, нагрев
не включается — причина остаётся в журнале. Панель показывает
состояние этого оборудования, но не управляет им.

**Поштучное управление остаётся за оператором.** Автоматика — основной
путь, но дым по ходу занятия добавляют, прожекторы гасят, а вытяжку
пускают раньше срока:

```
POST /api/v1/rooms/{id}/equipment  {"unit":"smoke","on":true}
```

Узлы: `smoke` (дымогенератор), `flood` (прожекторы), `strobe`
(стробоскоп), `sound` (звуки тренировки), `light` (освещение), `fan`
(вытяжка), `heat` (тепловая пушка). Состав берётся из раскладки
(`equipment:`), а без него — по виду помещения. Команда адресуется
сборщику комнаты, состояние узлов видно в `GET /api/v1/rooms` полем
`equipment` и переживает перезапуск центра.

В аварии поштучное управление недоступно (409): там выходами
распоряжается аппаратная петля. Возврат помещения в «Ожидание» гасит
всё.

Подготовку не начать, пока не записан состав:

```
POST /api/v1/rooms/{id}/roster   {"team":"Звено 1","rescuers":["…","…"]}
```

ФИО и ИИН вносят **до** подготовки: прогрев и дым стоят времени и
ресурса, и включать их, не зная, кто придёт, незачем. Запрос
подготовки без состава отклоняется (409). Занятие потом открывается
по этому же составу, без повторного ввода, а возврат комнаты в
«Ожидание» очищает его — следующей группе прошлый список не
принадлежит.

Настройки — в `rooms.yaml`:

```yaml
    prepare:
      target_c: 40      # целевая температура; без неё только таймер
      minutes: 30       # отведённое время
```

`GET /api/v1/rooms` отдаёт ход подготовки в поле `preparation`:
текущая и целевая температура, сколько секунд осталось, достигнута ли
цель и сообщение — «Идёт прогрев», «Комната готова» или «Температура
не достигнута».

Три правила из сценария, которые центр соблюдает:

- **тренировка начинается только из «Готова».** Попытка открыть
  занятие в «Ожидании» или «Подготовке» отклоняется: кнопка «Старт»
  по сценарию появляется после подтверждения готовности. Открытие
  занятия само переводит комнату в «Тренировку», завершение —
  в «Завершение»;
- **статус «Готова» сам не выставляется.** Достигнув цели, центр
  говорит «Комната готова», но в «Готову» комнату переводит
  администратор, осмотрев её;
- **время подготовки в тренировку не входит** — занятие открывается
  отдельно, и его таймер начинается с открытия.

У дымокамеры целевой температуры нет: она показывается для контроля,
а готовность подтверждает администратор. В `prepare` для неё задан
только `minutes`, чтобы подготовка не шла бесконечно.

### Упражнения и задания

Администратор задаёт задание тренажёру:

```
POST /api/v1/rooms/{id}/session/target  {"device":"…","seconds":600}
POST /api/v1/rooms/{id}/session/assign  {"device":"…","iin":"…"}
```

**Велоэргометр и лестница зачитываются по времени**: спасатель
работает отведённый срок, а метры, ступени и этажи показываются для
наблюдения и в зачёт не идут. Задание в подъёмах этим тренажёрам не
ставится — центр его отклоняет. У ударного молота зачёт по подъёмам
(`"reps": 20`).

Цель относится **к тренажёру, а не к человеку**: сменившийся спасатель
выполняет то же задание. Пустое задание снимает цель.

`GET /api/v1/rooms/{id}` отдаёт поле `exercises` — по одному на
тренажёр, в реальном времени и отдельно для каждого спасателя:

```json
{"device":"obj-17-bike-1","name":"Велоэргометр","iin":"…","busy":true,
 "seconds":18,"seconds_left":11,"distance_m":124.7,
 "target":{"seconds":30},"done":false}
```

Показатели считаются как **прирост от момента назначения**: счётчики
на платах накопительные и между заездами не обнуляются. Поэтому при
смене участника результат завершённого упражнения остаётся за
прежним, а новый отсчёт начинается с нуля.

Для лестницы правило пересчёта задаётся в раскладке:

```yaml
      - {id: obj-17-stairs-1, kind: stairs, steps_per_floor: 16}
```

Без него берётся то, что насчитала сама плата.

### Подъёмы на ударном молоте: задание и сверка

Норму задаёт оператор до упражнения, считает подъёмы плата, а в
отчёте оба числа стоят рядом:

```
Ударный молот, 25 кг — Иванов Пётр Сергеевич, 0:43,
подъёмов задано 5, выполнено 7 — норма выполнена
```

```
POST /api/v1/rooms/{id}/session/target  {"device":"obj-17-load-1","reps":20}
```

Зачёт закрывается по показаниям платы, а не по тому, что набрали в
панели: заданное — это требование, выполненное — измерение, и
сверяют их именно потому, что они могут разойтись. В записи занятия
они лежат рядом (`lifts_target` и `lifts`), поэтому сверка видна и на
экране результатов, и в PDF.

Подъёмы — единственный счётчик зачёта на объекте: велоэргометр и
лестница зачитываются по времени, и срок у них общий на оба
тренажёра.

### Завершение занятия и карточка

```
POST /api/v1/rooms/{id}/session/finish  {"reason":"…","comment":"…"}
POST /api/v1/sessions/{id}/comment      {"comment":"…"}
```

Завершение останавливает таймеры и учёт, закрывает видеозапись и
сохраняет всё в карточках участников. В карточке по сценарию §6
доступны:

| Что | Где в ответе |
|---|---|
| Дата, время и продолжительность | `started`, `seconds` |
| Время каждого упражнения | `assignments[].seconds` |
| Подъёмы, дистанция, ступени и этажи | `assignments[].result` |
| Температура помещения за занятие | `temp`: `min_c`, `max_c`, `avg_c` |
| Видеозапись | `records[].url` |
| Отметки заданий: когда и каким способом | `tasks[]`: `seconds`, `auto`, `by` |
| Попытки ввода кода и его значение | `attempts`, `code` |
| Комментарий администратора | `comment` |
| Причина досрочного завершения | `reason` |
| Итоговый статус | `status`, `outcome` |

Температура считается из истории телеметрии за время занятия, а не
копится отдельно: второй источник правды о том же датчике разошёлся
бы с первым. Без MongoDB истории нет, и сводка остаётся пустой —
карточка об этом честно молчит (`samples: 0`).

Статус занятия — три значения: «Выполнена успешно» (`success`,
пройден весь маршрут), «Не завершена» (`partial`, занятие закрыли
раньше) и «Прервана» (`aborted`, авария или решение администратора).
Он **записывается при закрытии занятия**, а не считается при чтении
карточки: маршрут комнаты со временем меняют, а зачёт выставлен по
тому, что было в тот день. Прерванное занятие остаётся прерванным,
даже если задания успели отметить.

Время прохождения задания (`tasks[].seconds`) считается от старта
тренировки, а не от предыдущей отметки: по сценарию §6 в карточку
идёт именно оно. Способ подтверждения сохраняется рядом — `auto`
означает сигнал тренажёра, иначе в `by` стоит отметивший
администратор.

Видеозапись охватывает **только занятие**: она начинается вместе с
таймером и закрывается при завершении, подготовка помещений в ролик
не входит. У секции пишутся камеры всех комнат маршрута, поэтому у
дымокамеры в карточке два ролика — по комнате на каждый. Трансляция
Live от записи не зависит и продолжает идти после её закрытия: это
разные процессы на одну камеру.

Комментарий пишется при завершении и правится потом отдельным
запросом: разбор бывает не сразу.

### Видеозапись занятий

Запись начинается вместе с таймером занятия и останавливается при его
завершении — в том числе аварийном. Ролик охватывает **только время
занятия**: подготовка в него не входит (сценарий §6).

```
MCHS_RECORDS=/records   каталог роликов; пусто — записи не ведутся
MCHS_RECORD_HOURS=4     предел длительности одной записи
```

На каждую камеру комнаты — свой процесс ffmpeg, параллельно
трансляции: тянуть один поток на две задачи нельзя, обрыв записи
уронил бы и Live. Видео пишется как есть, без перекодирования.

Ролики лежат в `/records/<занятие>/<камера>.mp4` и отдаются тем же
центром; ссылки приходят в занятии и в истории карточки:

```json
"records": [{"camera": "room1-cam-1", "url": "/records/…/room1-cam-1.mp4",
             "seconds": 1800, "bytes": 1048576000, "ok": true}]
```

Два решения, которые стоит знать:

- **фрагментированный MP4** (`frag_keyframe+empty_moov`). У обычного
  MP4 заголовок дописывается в конце, и убитый процесс оставил бы
  нечитаемый файл. Здесь оборванная запись всё равно воспроизводится;
- **предел длительности**: занятие могли забыть закрыть, и без него
  запись шла бы, пока не кончится диск.

Объём — около 1 ГБ на получасовую тренировку с двух камер; расчёт на
листе «Объёмы видео» в [docs/network-plan.xlsx](docs/network-plan.xlsx).
Ролики живут в томе `records`, а не в tmpfs: они приобщаются к
карточкам и должны пережить перезапуск.

### Состояния комнат и аварийная остановка

Комната проходит состояния сценария: «Ожидание» → «Подготовка» →
«Готова» → «Тренировка» → «Завершение». Порядок проверяется центром:
в «Готову» нельзя попасть минуя подготовку, а «Тренировка» наступает
**открытием занятия**, а не переключателем — иначе экран показывал бы
тренировку, которой нет в журнале.

```
POST /api/v1/rooms/{id}/state   {"state":"preparing","reason":"прогрев"}
POST /api/v1/alarm              {"reason":"нажата кнопка у входа"}
```

Авария объявляется из любого состояния и сразу во всех комнатах. Центр
при этом:

- закрывает открытые занятия с отметкой о причине — результаты и
  видеозапись сохраняются в карточках, а не пропадают вместе с аварией;
- шлёт каждому сборщику команду `alarm`. Команда адресуется **сборщику
  комнаты**, а не отдельным реле: он знает свою обвязку и переводит
  выходы в безопасное состояние разом — включает светильники и вытяжку,
  отпускает замки, останавливает управляемые тренажёры, снимает дым,
  стробоскопы, прожекторы, тепловые пушки и имитаторы очагов, глушит
  тренировочные звуки и объявляет «Аварийная остановка. Просим
  покинуть помещение тренировки». Центру не нужно знать, на каком
  выводе какое реле;
- **магниты «Завалов» при этом не трогаются**: они управляются
  отдельно от дверных замков, иначе аварийное открытие дверей
  обрушило бы трубы. Безопасное состояние механизма задаёт его
  конструкция;
- пишет событие в журнал: когда, почему, кто, какие комнаты и какие
  занятия затронуты.

```
GET /api/v1/alarms?limit=50
```

В карточках участников прерванные занятия сохраняются с отметкой
**«Аварийная остановка»** (`outcome: alarm`) — вместе с результатами,
отметками заданий и видеозаписями. Отметка отличается от обычного
досрочного завершения: по ней видно, что тренировку остановила
авария, а не администратор.

Трансляция Live при аварии не прерывается — камеры нужны как раз
тогда, когда участники выходят.

Обратно из аварии только в «Ожидание» и только вручную: сброс кнопки
работу не возобновляет. При выходе сборщику уходит `alarm_reset` —
разрешение работать, а не команда включиться; запуск делает
администратор, проверив готовность.

Сборщик комнаты задаётся в раскладке:

```yaml
    collector: obj-17-rpi-1
```

> Это **дублирование аппаратной петли**, а не замена ей. Нагрузку
> снимает реле безопасности, центр лишь останавливает учёт и
> сохраняет записи.

Состояния переживают перезапуск центра: комната, оставшаяся в аварии,
о ней не забывает.

`GET /api/v1/rooms` отдаёт всё, что нужно главному экрану: состояние
и когда оно наступило, температуру воздуха (с датчика пушки),
показания тренажёров, открытое занятие с карточками участников,
камеры и список неисправностей — пропавшие тренажёры, упавшие камеры,
перегрев.

### Картотека спасателей

Карточка заводится один раз и живёт дольше любой тренировки: к ней
привязывается история занятий. Опознаётся спасатель по **ИИН** — он
уникален, и вторую карточку с тем же ИИН центр не создаст (`409`).

```
POST /api/v1/rescuers              {"iin":"…","name":"ФИО","unit":"СЧ-2"}
GET  /api/v1/rescuers?q=&archived= поиск по ФИО, ИИН и подразделению
GET  /api/v1/rescuers/{iin}        карточка вместе с историей тренировок
PUT  /api/v1/rescuers/{iin}        правка ФИО и подразделения
POST /api/v1/rescuers/{iin}/archive вывести из обращения или вернуть
```

Формат ИИН не проверяется: номера заносятся вручную и в произвольном
виде. Центр относится к ИИН как к ключу — требует непустоту и
уникальность, а пробелы внутри убирает, чтобы «123 456» и «123456»
не завели двух карточек на одного человека.

Удаления нет: к карточке привязаны прошлые тренировки, и удаление
оставило бы в архиве записи без человека. Вместо него — архив.
Архивную карточку нельзя назначить на занятие (`400`).

Заводит и правит карточки оператор; читать картотеку вправе любой
вошедший — без списка не назначить участников.

### Секции: одно занятие на несколько комнат

Теплокамера — одна комната, дымокамера — две: команда проходит их
подряд, но таймер, видеозапись и зачёт у неё **общие** (сценарий
дымокамеры §3). Поэтому занятие открывается на секцию:

```yaml
sections:
  - {id: heat,  name: "Теплокамера", rooms: [room-1]}
  - {id: smoke, name: "Дымокамера",  rooms: [room-2, room-3]}
```

Что это даёт: занятие видно в обеих комнатах секции, задания обеих
комнат идут одним списком маршрута, записываются камеры обеих, а
начать тренировку можно только когда **все** комнаты секции готовы.
Завершение закрывает их разом.

Комната без секции считается секцией из самой себя — объект без
описанных секций работает по-прежнему.

### Команда и задания маршрута

Тренировку проходит **команда**, а карточки входят в её состав:

```
POST /api/v1/rooms/{id}/session  {"team":"Звено 1","rescuers":["…","…"]}
```

Результат, ролики и отметки связываются с карточкой каждого участника.
Размер команды ограничен вместимостью комнаты (`capacity`).

Маршрут комнаты задаётся в раскладке; задание проходит команда
целиком, поэтому отметка одна:

```yaml
    tasks:
      - {id: maze, name: "Лабиринт в три уровня", note: "Найти выход"}
      - {id: code, name: "Набор чисел", device: obj-17-code-1}
```

Задание с `device` отмечается **само**, по сигналу устройства: верный
код со стойки, отключённый имитатор очага. Без `device` отмечает
администратор:

```
POST /api/v1/rooms/{id}/session/task  {"task":"maze","done":true}
```

Сигнал, пришедший до начала занятия, не засчитывается — иначе задание
зачлось бы предыдущей команде. `GET /api/v1/rooms/{id}` отдаёт список
заданий с отметками: кто и когда отметил, вручную или сигналом.

**Задание «Набор чисел»** (сценарий дымокамеры §4): при старте
подготовки центр формирует новый четырёхзначный код, отправляет его на
панель командой `set_code` и показывает администратору — тот сообщает
код участникам до старта. Код виден в комнате (`code`) и попадает
в занятие и карточку.

Неверный ввод задание не завершает, но учитывается: число попыток
считается из истории телеметрии и записывается в карточку
(`attempts`). Код формируется заново на каждую тренировку — иначе
следующая команда пришла бы с подсказкой от предыдущей.

> Автоматические отметки — черновик: контракт этих устройств пока
> не согласован, и центр засчитывает то, что уже есть в протоколе
> (событие кода и событие реле).

**Завалы** включает администратор по ходу маршрута — отдельной
командой комнате, а не переключателем оборудования:

```
POST /api/v1/rooms/{id}/rubble
```

Команда `rubble` уходит сборщику комнаты и принимается **только во
время тренировки**: вне её центр отвечает 409, чтобы имитатор не
оказался под напряжением в пустом помещении.

**Полное прохождение маршрута завершает занятие само.** Когда отмечено
последнее задание — вручную или сигналом устройства, — центр закрывает
занятие, сохраняет результат в карточках и шлёт сборщику `announce`
со звуком `success`: оповещение в комнате слышат те, кто внутри, и
администратору не нужно закрывать занятие вручную. Для секции
учитываются задания всех её комнат: одно занятие дымокамеры
завершается, когда пройдены маршруты и комнаты 1, и комнаты 2.

Температура помещения берётся с тепловой пушки, а если её нет — с
датчика воздуха, указанного полем `sensor`. В дымокамере пушки нет и
датчик свой на каждую комнату: помещения греются и задымляются
по-разному, и одно показание на обе ничего не сказало бы о второй.

```yaml
    sensor: obj-17-smoke-temp-2   # комната 1
    sensor: obj-17-smoke-temp-3   # комната 2
```

### Занятие: состав и зачёт

Состав записывают до подготовки (см. выше), и показания становятся
чьими-то с самого начала: без имени поток чисел нельзя приобщить к
зачёту — через час никто не вспомнит, чей был заезд.

Пока занятие идёт, в помещении видно состав, время на тренажёрах и
кто открыл занятие. По завершении центр считает результат как
**разницу счётчиков** на момент открытия и закрытия: счётчики на
платах накопительные и между заездами не обнуляются.

**Велоэргометр и бесконечная лестница зачитываются по времени.**
Спасатель работает отведённый срок, и в зачёт идёт таймер, а не метры
и этажи. Поэтому ни панель, ни отчёт не выносят рядом с таймером путь
и пройденные этажи: скорость и расстояние считаются из длины
окружности колеса, которую никто не задаёт, и означали бы точность,
которой нет. Для наблюдения остаются обороты и ступени — по ним видно,
работает человек или стоит. У ударного молота зачёт по подъёмам:

```
Велоэргометр — Иванов П. С., 5:00 · Ударный молот — Петров И. О., 4:12, подходов 5
```

Занятие открывается **по карточкам**: в теле `{"rescuers":["ИИН", …]}`.
Тогда имя занятия собирается из картотеки, а не из поля ввода, и
занятие попадает в историю каждого участника — звеном могут заниматься
несколько человек. Поле `examinee` остаётся для занятия без карточки.

Правила: занятие открывает и закрывает только оператор (наблюдателю —
403); второе занятие в той же комнате не открыть, пока не закрыто
первое (409) — иначе показания зачлись бы двоим; ФИО нормализуется
(лишние пробелы) и проверяется мягко: дефис, апостроф и точка
разрешены, цифры и разметка — нет.

Имя оператора берётся из его сессии, а не из тела запроса: журнал
занятий бессмыслен, если в нём то, что клиент о себе написал.

Занятия и сессии операторов хранятся в MongoDB и переживают
перезапуск центра: открытое занятие остаётся открытым, журнал заездов
на месте, дежурному не приходится входить заново. Без базы центр
работает по-прежнему, но предупреждает в журнале, что теряет это при
перезапуске.

Правило «одно открытое занятие на комнату» держится уникальным
частичным индексом в базе, а не только проверкой в коде: два
оператора, нажавшие «начать» одновременно, не создадут двух заездов.

### Лестница и силовая установка: контракт в согласовании

Платы этих тренажёров ещё не шлют данные. Контракт описан и
реализован в центре и панели, документ для согласования с
изготовителем — [CONTRACT-DRAFT.md](../telemetry/CONTRACT-DRAFT.md).
Такие виды помечены в API полем `draft`, а в панели — подписью
«контракт в согласовании».

Данные для проверки даёт имитатор комнаты — он шлёт телеметрию всех
тренажёров сразу, батчами на вход сборщика:

```
scripts/simulate-room.sh http://127.0.0.1:8080 operator пароль
```

## Запуск на Windows-хосте

Весь сервис живёт в Linux-контейнерах, поэтому на хосте нужен только
**Docker Desktop (WSL 2)**. Ни Go, ни Node, ни ffmpeg, ни Python на
Windows ставить не требуется: бинарь, панель и имитатор собираются и
работают внутри образов.

```powershell
cd \data\center
copy rooms.example.yaml rooms.yaml      # вписать свои камеры
docker compose up -d --build
```

Открыть `http://localhost:8080` — панель раздаёт сам центр, с того же
адреса идут API, поток событий и видео.

Что стоит знать:

- **Учётные записи.** Утилита лежит в образе, Go на хосте не нужен:

  ```powershell
  docker compose run --rm -v ${PWD}:/work --entrypoint /mchs-users `
    telemetryd-video -file /work/users.json -login operator -role operator
  ```

  Она спросит пароль и запишет `users.json` рядом с `compose.yaml`;
  тот же файл сервис монтирует себе при запуске. Список — ключом
  `-list`, удаление — `-remove <логин>`.
- **Имитатор комнаты** запускается контейнером, без Python на хосте:
  `docker compose --profile sim up simulator`
  (пароль оператора — в переменной `MCHS_PASSWORD`).
- **Скрипты `scripts/*.sh` и `make`** рассчитаны на Linux-оболочку;
  на Windows они нужны только разработчику и работают в WSL.
- **Переводы строк.** Если правите `rooms.yaml` или `users.json`
  блокнотом, CRLF не мешает: YAML и JSON их переносят. А вот
  `scripts/*.sh`, сохранённые с CRLF, в WSL не запустятся.
- **Сборка образа** требует соседние каталоги `../telemetry` и
  `../panel`: они приходят именованными контекстами,
  поэтому репозитории должны лежать рядом.

Нативная сборка под Windows (`GOOS=windows`) сейчас не поддерживается:
видеоадаптер завершает ffmpeg через группу процессов Unix. Если
понадобится запуск без Docker, это разводится по платформам —
отдельными файлами с `//go:build`.

## База центра

История телеметрии, журнал занятий и сессии операторов лежат в
MongoDB, которая поднимается контейнером вместе с профилем `video`.
Наружу порт не публикуется: база нужна только центру, и внутри сети
compose он находит её по имени сервиса.

Решение держать её в контейнере, а не брать системную MongoDB узла,
принято намеренно: объект разворачивается одной командой и
воспроизводится одинаково на Linux и на Windows, а данные центра не
перемешиваются с чужими базами машины.

Плата за это — том Docker, который легко потерять вместе со стеком
(`docker compose down -v`) или при переустановке узла. Поэтому есть
выгрузка:

```
make db-dump                                  # в ./backups
make db-restore FILE=backups/mchs-20261017-012957.archive.gz
```

Выгрузка — один сжатый файл: его проще унести с объекта и положить
обратно. Восстановление заменяет содержимое базы (`--drop`) и
спрашивает подтверждение; `MCHS_DB_RESTORE_FORCE=1` снимает вопрос.

Снимать копию стоит после каждой смены — в журнале занятий лежат
результаты зачётов, и терять их нельзя.

## Автозапуск при включении

Контейнеры помечены `restart: unless-stopped` и возвращаются сами,
как только поднялся демон Docker. Кто запускает сам Docker — зависит
от узла: на Linux это юниты systemd из `deploy/systemd`, на Windows —
задача планировщика из `deploy/windows`, потому что Docker Desktop
живёт в сеансе пользователя и без входа не стартует.

Подробно, с оговорками и проверками: [docs/autostart.md](docs/autostart.md).

## Видеонаблюдение

Камеры описываются в YAML-файле — его правит инженер на объекте,
пересборка не нужна. Образец: [cameras.example.yaml](cameras.example.yaml).

```yaml
cameras:
  - id: cam-101                 # латиница, цифры, «-», «_»: попадает в адрес
    name: "Въезд на объект"
    url: "rtsp://admin:${CAM_PASS}@192.168.1.64:554/Streaming/channels/101"
    transport: tcp              # tcp (надёжнее) | udp (задержка меньше)
    site: default
    location: "КПП"
    audio: false
    # disabled: true            # описана, но не поднимается
```

Пароль можно не держать в файле: `${CAM_PASS}` подставляется из окружения.
Наружу — в API, в журнал, в сообщения об ошибках — адрес уходит только
с замаскированным паролем.

```
go run ./cmd/telemetryd -cameras cameras.yaml -video-root /tmp/mchs-video
```

Как это работает:

1. `ffmpeg` забирает RTSP с камеры и перекладывает его в HLS **без
   перекодирования** (`-c:v copy`): камера уже отдаёт H.264, поэтому
   нагрузка на процессор близка к нулю и один узел ведёт десятки камер.
2. Сегменты и плейлист пишутся в `-video-root`; старые удаляются, на
   диске всегда лежит только окно в `-video-window` сегментов.
3. Тот же сервис отдаёт их по `/video/{id}/index.m3u8`. Плейлист —
   с `Cache-Control: no-store`, сегменты — как неизменяемые.
4. Упавшую камеру надзор поднимает заново с нарастающей паузой
   (1 с → 30 с, с разбросом, чтобы камеры объекта не ломились разом).
   Замерший поток — когда `ffmpeg` жив, а плейлист не обновляется —
   считается срывом и тоже ведёт к перезапуску.

Задержка у зрителя — около двух-трёх сегментов, то есть 4–6 с при
настройках по умолчанию. Для диспетчерской этого достаточно; если
понадобится меньше секунды, добавляется вторая реализация
`port.StreamPublisher` под WebRTC — прикладной слой не меняется.

### Панель: что где лежит

Панель (`/data/panel`) — **не одностраничное
приложение**: каждый раздел собирается в свою страницу со своим
адресом и своим бандлом. Дежурные ведут комнаты одновременно, и
каждому нужно своё окно, которое можно обновить, свернуть и вынести на
второй монитор, не задевая чужое.

| Страница | Что на ней |
|---|---|
| `index.html` | обзор комплекса: камеры Live, температура, состояние, команда в зале, прогресс маршрута, неисправности, журнал аварий |
| `room.html?room={id}` | комната: подготовка и состояния, код для стойки, назначения, упражнения с таймерами, маршрут с отметками и «Включить завалы», тренировка, тренажёры, камеры |
| `team.html?room={id}` | **сбор звена** — отдельное окно: ФИО и ИИН вводят до тренировки, здесь же заводят новую карточку; окно открывает занятие и закрывается само |
| `results.html` | результаты: журнал занятий объекта, разбор выбранного, ссылки на PDF-отчёт и видеозаписи, комментарий администратора |
| `cards.html` | картотека: заведение, поиск, архив, тренировки участника |
| `devices.html` | телеметрия: плоский список устройств, графики, уставки, журнал команд |

Порядок работы задан сценарием: **сперва состав, потом тренировка**.
На экране комнаты полей ФИО и ИИН нет намеренно — там следят за залом,
а состав набирают в своём окне у входа.

Раскладка горизонтальная: карточки идут в два-три столбца и
заполняют экран по ширине, прокрутка — внутри страницы, а не у всего
документа. На узком экране столбцы схлопываются в один.

### Отчёт о тренировке

На каждое занятие центр складывает **отдельную папку** — её отдают
целиком, поэтому PDF и видеозаписи лежат рядом:

```
records/reports/2026-10-20/22-22-room-2-Звено-16/
├── report.pdf
└── video/
    ├── room2-cam-1.mp4
    └── room2-cam-2.mp4
```

Имя папки читается глазами: дата, время, комната, звено. Ролики в неё
**переносятся**, а не копируются, — папка отчёта лежит на том же томе,
и перенос стоит переименования.

В отчёте то же, что в карточке (сценарий §6): дата и время, звено и
состав, продолжительность, задания с временем от старта и способом
подтверждения, попытки кода, условия в помещении, упражнения,
перечень роликов, комментарий и итоговый статус. Шрифт вшит в
двоичный файл центра: образ собирается из `scratch`, системных
шрифтов в нём нет.

```
GET /api/v1/sessions?limit=200        журнал занятий объекта
GET /records/reports/…/report.pdf     сам отчёт
```

Отчёт — приложение к зачёту, а не условие его сохранения: если его не
удалось сформировать, занятие всё равно закрывается, а причина
остаётся в журнале.

### Подключение панели

Статус камер и ссылки на трансляции панель берёт из `/api/v1/cameras`
(`playlist` непустой только когда камера в эфире). Браузеры, кроме
Safari, играют HLS через [hls.js](https://github.com/video-dev/hls.js):

```js
const cams = await fetch('/api/v1/cameras', {
  headers: { Authorization: `Bearer ${token}` },
}).then((r) => r.json());

for (const cam of cams.filter((c) => c.live)) {
  const video = document.querySelector(`video[data-cam="${cam.id}"]`);
  // Токен в адресе: плеер запрашивает сегменты сам и заголовков не ставит.
  const src = `${cam.playlist}?token=${token}`;

  if (video.canPlayType('application/vnd.apple.mpegurl')) {
    video.src = src;                       // Safari умеет сам
  } else {
    const hls = new Hls({ lowLatencyMode: true });
    hls.loadSource(src);
    hls.attachMedia(video);
  }
}
```

### В контейнере

Пустой образ `scratch` для видео не подходит — нужен `ffmpeg`,
поэтому для него есть отдельная стадия:

```
cp cameras.example.yaml cameras.yaml   # и впишите свои камеры
docker compose up -d --build
```

Сегменты лежат в `tmpfs`: они живут секунды и переписываются при каждом
запуске, так что память быстрее и бережнее к диску.

## Слои

```
cmd/telemetryd            сборка зависимостей, сигналы, завершение
internal/domain           модель телеметрии и её инварианты (без зависимостей)
internal/domain/video     модель камеры и состояния трансляции
internal/app/port         интерфейсы: Decoder, Sink, StateRepository, PacketSource
internal/app/ingest       сценарий приёма: валидация, сохранение, раздача, надзор
internal/app/query        сценарии чтения состояния
internal/adapter/inbound  udp (приём датаграмм), httpapi (чтение состояния)
internal/adapter/outbound codec (JSON), sink (консоль, CSV, Mongo), repo (память),
                          camyaml (камеры из YAML), ffmpeg (трансляция в HLS)
internal/config           флаги и переменные окружения
```

Зависимости направлены внутрь: адаптеры знают про `domain` и `port`,
прикладной слой — только про `domain` и `port`, домен — ни про кого.

## Точки расширения

- другой формат на проводе — новая реализация `port.Decoder`;
- новый приёмник (TCP, MQTT) — новая реализация `port.PacketSource`;
- отправка в БД/брокер — новая реализация `port.Sink`;
- постоянное хранилище — новая реализация `port.StateRepository`
  вместо `repo.Memory`;
- другой способ трансляции (WebRTC, MJPEG) — новая реализация
  `port.StreamPublisher` вместо `ffmpeg.HLS`;
- камеры из базы вместо файла — новая реализация `port.CameraRepository`.

## Тесты

```
go test ./...
```

Тесты хранилища идут против настоящей MongoDB: подменять драйвер
заглушкой бессмысленно — проверяются как раз индексы и поведение базы.
Временная база поднимается и удаляется сама:

```
make test-store
```

Чтобы прогнать их против уже работающей базы, задайте её адрес:

```
MCHS_TEST_MONGO=mongodb://127.0.0.1:27017 make test-store
```

Если на том сервере уже есть базы, скрипт перечислит их и спросит
подтверждение: на машине разработчика по адресу `127.0.0.1:27017`
обычно висит системная MongoDB, а не та, которая имелась в виду.
В неинтерактивном запуске он просто откажется. Снять вопрос —
`MCHS_TEST_STORE_FORCE=1` (для CI и для тех, кто точно знает, куда
целится).

Без этой команды обычный `go test ./...` остаётся зелёным: при
отсутствии `MCHS_TEST_MONGO` эти тесты пропускаются.
